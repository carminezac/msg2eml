# Conversion quality analysis

Message: `samples/<supplier-message>.msg` (157 KB).
Reference: `out/outlook-web-reference.eml`, export of the same mail from
Outlook Web.
Output: `out/msgconv.eml` (43 KB), generated with
`./tools/oneshot-msgconv/run.sh "samples/<file>.msg" out/msgconv.eml`.
Full reports: `out/conversion-report.txt`, `out/comparison-report.txt`.

## Characteristics of the source message

```text
Type                : Email
Subject             : [EXT]<message subject>
Sender              : Sender Name <sender@supplier.example>
SentOn              : 2026-09-04T13:14:41+00:00
BodyText            : 2130 characters
BodyHtml            : 10053 characters  (de-encapsulated from the RTF)
BodyRtf             : 20454 characters
TransportHeaders    : 21580 characters
Recipients          : 6  (1 To with AddressType=EX, 5 Cc SMTP)
Attachments         : 3  inline images, all Hidden=True, RenderingPosition=-1
```

The sample is more demanding than a trivial mail:

- **no native HTML property**: the HTML exists only inside the RTF and must be
  de-encapsulated — the path with the highest risk of fidelity loss;
- **`To` recipient in Exchange `EX` format**, not SMTP: resolvable only thanks
  to the transport headers;
- **HTML signature with 3 `cid:` images** marked `Hidden`, i.e. inline images
  disguised as hidden attachments;
- long transit chain (Exchange Online + Check Point gateway), hence many
  `Received` / `ARC-*` / `DKIM-*` headers to preserve.

## Results

### Headers

| Header | Outcome |
| --- | --- |
| `From`, `To`, `Cc`, `Subject`, `Date`, `Message-ID`, `Thread-Index` | identical to the reference |
| Total headers | 94 (ours) vs 64 (Outlook Web) |
| `Return-Path` | present in ours, removed by Outlook Web |

The original `Message-ID`
(`<id>@<host>.EURPRD10.PROD.OUTLOOK.COM`)
is preserved: essential for threading and for evidentiary use. The entire
`Received` chain, the `DKIM-Signature` signatures and the `ARC-*` seals, which
Outlook Web discards, are preserved as well. For archival purposes this is an
advantage: the conversion remains verifiable.

The `To` in `EX` format was resolved to the correct SMTP address
(`recipient@company.example`) because it was taken from the original header,
not from the MAPI property.

### Body

| Part | Reference | Output | Visible text |
| --- | --- | --- | --- |
| `text/plain` | 2128 chars, base64 | 2130 chars, quoted-printable | identical |
| `text/html` | 10019 chars, base64 | 9943 chars, quoted-printable | identical |

Comparison of the visible text of the HTML (tags removed, entities decoded,
whitespace normalised): **2022 identical characters in both**. Accents and
`€` correct; `charset=utf-8` declared on both parts.

### Inline images

| File | Size | sha256 (16) | Outcome |
| --- | --- | --- | --- |
| `image001.png` | 3379 B | `efeab7d3429ae11f` | byte-identical |
| `image002.png` | 955 B | `d7cadf0c1a72373b` | byte-identical |
| `image003.jpg` | 802 B | `3bcb49c0da97a496` | byte-identical |

The 3 `cid:` references in the HTML all resolve to an existing part, with
`Content-ID` identical to the original and `Content-Disposition: inline`.

### MIME validation

The Python stdlib `email` parser — independent of MimeKit — reopens the EML
with no `defects`, just like the Outlook Web file.

## Residual differences

### 1. Equivalent but different MIME structure

```text
Outlook Web                      Output
multipart/related                multipart/alternative
├── multipart/alternative        ├── text/plain
│   ├── text/plain               └── multipart/related
│   └── text/html                    ├── text/html
├── image001.png                     ├── image001.png
├── image002.png                     ├── image002.png
└── image003.jpg                     └── image003.jpg
```

Both valid under RFC 2387. Ours is semantically more precise: the images are
in `related` only with the HTML that uses them, not also with the alternative
text. No impact on rendering in clients.

### 2. `<meta http-equiv="Content-Type">` injected by Outlook Web

Outlook Web adds to the `<head>` a `<meta http-equiv="Content-Type"
content="text/html; charset=utf-8">` that does not exist in the original. It
is a difference *added* by the reference, not a loss on our side: `<head>`,
`</head>`, `<body>` and `</html>` are present in both files.

### 3. Line breaks normalised by the RTF de-encapsulator

MsgReader removes the leading space of the continuation lines generated by
Outlook. In the HTML it is invisible (non-significant whitespace, 19 lines
affected). In the `text/plain` it produces two extra spaces:

```text
-sender@supplier.example<mailto:sender@supplier.example>
+sender@supplier.example <mailto:sender@supplier.example>
```

Impact: cosmetic, 2 characters out of 2130. It makes no sense to fix it with
post-processing: manipulating the body violates the plan's principle
("preserve the original content, avoiding unnecessary transformations") and
risks breaking other messages.

### 4. Extra `Return-Path`

Kept by us, removed by Outlook Web. Higher fidelity to the original.

## Defects found and fixed during the spike

They must be carried into the service; they are errors that would recur.

1. **Windows-1252 encoding missing in Linux container.**
   `MsgReader.Rtf` calls `Encoding.GetEncoding("Windows-1252")`, not available
   in .NET Core on Linux → `ArgumentException` on every message with an
   RTF-encapsulated body, i.e. the majority of internal Outlook mails. Fix:
   `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)` at startup,
   with the `System.Text.Encoding.CodePages` package.

2. **Empty `From:` header at the top.**
   Building with `new MimeMessage()` and then copying the headers, MimeKit
   pre-creates an empty `From`: clients read the first `From` and show no
   sender. Duplicated `Date`, `Subject` and `Message-Id` also showed up.
   Fix: load the original headers *as a message* and remove only the body
   headers, instead of copying them into a new message.

3. **Missing `Content-Transfer-Encoding` on 8-bit parts.**
   MimeKit does not assign an encoding by itself: text with accented
   characters and `€` (29 non-ASCII bytes) was written 8-bit without declaring
   it, hence implicitly `7bit`. Non-compliant message, body liable to
   corruption when passing through a non-`8BITMIME` MTA. Fix:
   `mime.Prepare(EncodingConstraint.SevenBit)` before serialisation.
   `compare-eml.py` checks this condition.

## Conclusion

On a realistic, non-trivial case — HTML only inside RTF, Exchange sender,
signature with inline images — the conversion preserves original headers,
visible text, attachments and inline references, and produces valid MIME
according to an independent parser. The differences from Outlook Web are
matters of form, and in two places our output is more faithful to the
original.

The `.NET + MsgReader + MimeKit` stack is confirmed. We can proceed with the
action plan, starting from the three fixes above as requirements and from
`compare-eml.py` as the basis for the integration tests (point 8 of the plan).

**Validity limit: a single message.** Before the converter can be considered
reliable, the corpus of 10-20 files planned in point 17 of the plan must be
covered; the missing cases are listed in `02-playbook.md`, section 5.
